# Build Notes — how this was put together

A walkthrough of how the NIBM KIC Media Club app was built, in the order it was built, with the reasoning behind each decision. Written to be read alongside the code, not instead of it — file paths are given so you can open the real thing next to each section.

Everything described here is verified against the working tree. Two large pieces of `CLAUDE.md` are **not** built and are not described as if they were: the suggestion-clustering engine (TF-IDF/KMeans, `/suggestions/analyse`, `/suggestions/themes`, the Themes view), and **authentication**. See "What's deliberately absent" at the end for the full list.

---

## 0. Starting point: a domain mismatch

The repo wasn't empty — it had a prior project scaffolded into it (a photography-studio proofing app: clients, shoots, image culling, selects). None of that matched `CLAUDE.md`, which specs a completely different app. First move, before writing anything: read the existing models (`backend/app/models/*.py` at the time) to confirm the mismatch, then ask rather than guess whether to replace it, keep both, or stop. Rule of thumb worth keeping: when a codebase's actual state contradicts its spec, that's a decision for whoever owns the project, not something to silently work around.

Once told to replace it, everything under the old domain was deleted (`client.py`, `shoot.py`, `image.py`, `job.py`, `magic_link.py`, `select.py`, `edit_request.py`, `final.py`, `studio_user.py`, plus their tests and the `shoot_status.py` state-machine service) and rebuilt from `CLAUDE.md` section 8's table definitions.

---

## 1. Data model (`backend/app/models/`, `backend/alembic/`)

**Reusable infra kept from the old scaffold**, because it was domain-agnostic and already solid:
- `app/db/base.py` — `Base` (declarative base with an explicit constraint-naming convention, so every index/FK/unique constraint gets a predictable name like `fk_photos_event_id_events` instead of an autogenerated hash), `UUIDPrimaryKey` mixin, and a `CreatedAt` mixin (swapped in place of the old `Timestamps` mixin, which also had `updated_at` — none of the five new tables need it, so it was dropped rather than carried along unused).
- `app/models/enums.py`'s `pg_enum()` helper — makes SQLAlchemy store a Postgres native enum by *value* (e.g. `"event-idea"`) rather than by Python member name (`EVENT_IDEA`), which matters because the wire format has to match `CLAUDE.md`'s fixed category list exactly.

**Five tables**, one file each (`user.py`, `event.py`, `photo.py`, `committee_member.py`, `suggestion.py`), columns copied verbatim from `CLAUDE.md` section 8 — deliberately not embellished with extra columns "while I'm in there." Two relationships worth noting:
- `Event.photos` and `User.suggestions` both cascade-delete (`cascade="all, delete-orphan"` on the ORM side, `ondelete="CASCADE"` on the FK itself — both matter: the DB-level one protects raw SQL deletes, the ORM-level one keeps in-memory objects consistent within a session).
- `Suggestion.theme_id`/`theme_label`/`sentiment` exist as columns now even though nothing writes them yet — they're there so the future clustering engine has somewhere to land results without a schema change.

**Migration**: `alembic revision --autogenerate -m "initial schema"` diffs the models against an empty database and writes the migration for you — you don't hand-write `CREATE TABLE` statements. One thing autogenerate *doesn't* catch: it won't emit `DROP TYPE` for Postgres enums on downgrade, so `alembic/versions/b793dd612c10_initial_schema.py`'s `downgrade()` has four manual `op.execute("DROP TYPE IF EXISTS ...")` lines added by hand — worth knowing autogenerate needs a human read-through, not a blind accept.

**Tests** (`tests/test_models.py`, `tests/test_migrations.py`) run against two different mechanisms on purpose: `test_models.py` uses `Base.metadata.create_all()` (fast, tests the ORM layer), `test_migrations.py` actually runs `alembic upgrade`/`downgrade` against a throwaway database (slower, but it's the only thing that proves the *migration file* — not just the models — is correct; they can drift apart if you ever hand-edit one without the other).

**Seed script** (`backend/seed.py`): truncates and reinserts rather than checking "does this exist" row by row — simpler, and safe because it's dev-only data.

## 2. Auth — built, then removed

`CLAUDE.md` section 9 specifies `/auth/register`, `/auth/login`, `/auth/me`, and a two-role (`student`/`admin`) JWT gate on every write endpoint. **None of that is in the tree.** An auth layer was built and then taken back out; the migration that did it is still there to read: `backend/alembic/versions/482b38f57f84_drop_auth_columns_from_users.py`.

What that means concretely, and worth confirming for yourself rather than taking on trust:
- `backend/app/models/user.py` has `name`, `email`, `batch`, `student_id` — **no `password_hash`, no `role`**.
- There is no `app/core/security.py`, no `app/core/deps.py`, no `app/routers/auth.py`, no `app/schemas/auth.py`.
- `backend/app/main.py` registers exactly three routers: `events`, `committee`, `suggestions`.
- `admin/src/api/client.ts` is a bare Axios instance — **no JWT interceptor**, no `localStorage` token read.

So every endpoint the contract marks "admin" is currently **open**. The admin panel is not access-controlled; it is a UI over an unauthenticated API. That is fine for local development and is the single biggest thing to fix before this is exposed anywhere. It also means the `is_anonymous` handling in section 3 is doing real work for a different reason than you'd assume — it protects student identity from anyone who can reach the API, which right now is anyone at all.

This is the most important entry in these notes: **a spec describing a feature is not evidence the feature exists.** Check the model, the router registrations, and the HTTP client before believing a doc.

## 3. Events, photos, committee (`backend/app/routers/events.py`, `committee.py`)

**Slugs are server-generated.** `app/services/slug.py`'s `unique_event_slug()` lowercases + hyphenates the title, then checks the DB in a loop, appending `-2`, `-3`, etc. on collision. The client never sends a slug — this is in the API contract explicitly ("slug is server-generated, never client-supplied") so two clients (React, Flutter) can't disagree about how to slugify.

**The published/draft visibility rule** is the one bit of business logic in this router worth studying closely (`list_events` in `events.py`): `GET /events` with no `status` query param defaults to `published` only, but an explicit `?status=draft` returns drafts. This one default does two jobs at once — the student-facing Flutter app never has to think about hiding drafts (it just never passes `status`), and the admin UI can still list drafts by asking for them explicitly. No auth check needed on this endpoint at all; the filtering *is* the access control.

**Cover photo has no dedicated column.** `Event.cover_image_url` just holds whichever photo URL was chosen — "set cover" in the admin UI is a plain `PATCH /events/{id}` with that field, not a special endpoint. Fewer moving parts than a `Photo.is_cover` boolean that has to stay in sync (what happens when you delete the cover photo? now you'd need a trigger or app-level cleanup — the URL-copy approach sidesteps that entirely, at the cost of the cover photo's other fields, like caption, not being reachable from the event).

**A contract gap, kept rather than papered over**: `CLAUDE.md`'s feature list mentions photo reorder, but the frozen API surface (section 9) only has `POST` (append) and `DELETE` on photos — no reorder endpoint. Rather than inventing an undocumented `PATCH`, the router just doesn't support it, and both the plan doc and the React admin code have one-line comments flagging it. Same situation, same treatment, for committee-member editing (`POST`/`DELETE` only, no `PATCH`). When a spec's prose and its frozen contract disagree, the contract wins, and the gap gets written down instead of silently patched.

## 4. Suggestions — submission side only (`backend/app/routers/suggestions.py`)

The interesting piece here is **anonymity enforcement**, because it's a case where "hide it in the UI" isn't good enough. `CLAUDE.md`'s decision table says `author_id` is kept internally (for abuse control) but hidden from every response when `is_anonymous` is true. That's done in `_to_admin_response()`: the function builds the response object itself, field by field, and explicitly sets `author_name`/`author_batch` to `None` when the suggestion is anonymous — it never serializes the full `User` object and trusts the frontend not to display two of its fields. If you only hid it in React, anyone with browser devtools would see it in the network tab. Enforcing it server-side, at the point where the response is constructed, means there's nothing to leak regardless of which client asks.

A secondary effect of that design: admin filtering by `batch` still works even for anonymous suggestions (`list_suggestions` joins on `User.batch` in the query) — the *query* can use the real author, the *response* just never echoes it back. Filtering and hiding are separate concerns and don't have to trade off against each other.

**Validation**: suggestion body length (10–2000 chars) is a `Field(min_length=10, max_length=2000)` on the Pydantic schema, checked before anything touches the database — same "validate at the boundary" pattern as the email check in auth.

What's *not* here: `theme_id`/`theme_label`/`sentiment` are always `None` on every response, because nothing ever sets them — that's the clustering engine's job, not built.

## 5. Freezing the contract (`docs/api-contract.md`, `docs/data-model.md`)

Once the endpoints existed and were tested, they got written down in `docs/api-contract.md` — exact request/response JSON for every endpoint, including the two "not yet implemented" ones (`/suggestions/analyse`, `/suggestions/themes`) called out explicitly so nobody builds UI against them by accident. This is the point `CLAUDE.md` calls "the contract freezes" — from here on, the two frontends were built entirely from this document, not by reading the backend source. That's the actual test of whether a contract doc is good enough: can someone build against it without opening the implementation? Both frontend builds did exactly that.

`docs/data-model.md` is the same idea one layer down — a table-by-table reference of the schema, so "what columns does `suggestions` have" doesn't require opening `suggestion.py`.

## 6–7. React admin (`admin/`)

Built by a fresh agent working *only* from `CLAUDE.md` and `docs/api-contract.md` — a deliberate test of whether the contract doc was actually sufficient. It was: no round-trips back to the backend source were needed.

Structure is `src/{api,components,pages,types}` plus a `test/` folder. Note this is **`CLAUDE.md` section 10 minus `hooks/`** — that folder was specified for the auth hook, and with auth gone there was nothing left to put in it, so it doesn't exist. Layering:
- `types/index.ts` — TypeScript interfaces matching the API's JSON shapes one-to-one (kept snake_case to match the wire format rather than converting to camelCase — one less translation layer to get wrong).
- `api/*.ts` — one file per resource, one function per endpoint, nothing extra. `api/client.ts` holds the single Axios instance plus `getErrorMessage()`, which normalizes both FastAPI error shapes (`{"detail": "string"}` for `HTTPException` and `{"detail": [...]}` for Pydantic validation failures) into one string the UI can render. Read it — it is small, and it is the reason no page has to branch on error shape.
- `pages/*.tsx` — one per screen, each pulling data via TanStack Query (`useQuery`/`useMutation`), which handles loading/error states and cache invalidation after mutations (e.g. creating an event invalidates the `["events"]` query key so the list refetches).
- `components/` — `Layout.tsx` (sidebar + top bar), `PageHeader.tsx` (title/description/actions, used by every page so headers can't drift apart), `ErrorBanner.tsx`.

**There is no login page and no route guard.** `App.tsx` renders all five routes unconditionally. The sidebar footer shows a hardcoded name and email; it is a label, not a session.

**Dashboard has no backend endpoint** — it's `useQuery` calls to `/events` and `/suggestions`, counted client-side. Fine at this scale; would need a real aggregation endpoint if the data ever grew past "fits in one response." One wrinkle worth reading in `DashboardPage.tsx`: `GET /events` with no `status` returns published only, so the dashboard fires *two* requests (default + `?status=draft`) and merges them. That's the visibility rule from section 3 leaking into every admin caller — the cost of making the student case the default.

No Themes view exists — skipped outright, matching the contract doc's "not yet implemented" note.

## 7. The admin's visual design system (`admin/src/index.css`, `components/Layout.tsx`)

The first version of the admin used generic glassmorphism — frosted translucent panels, a grey `surface-*` ramp, an amber accent on a near-black gradient hero. It looked like a template. This pass replaced it with a system derived from the club's own brand mark. Several transferable lessons came out of it.

**Sample the palette, don't invent it.** The colours were read directly out of `admin/public/logo.png` by counting pixels, which produced royal navy `#29458F` and marigold gold `#E4A830`. Guessing "navy" would have landed on a generic dark blue that sits slightly wrong next to the real logo; sampling guarantees the UI and the mark agree.

**Tokens live in one place.** `index.css` uses Tailwind v4's `@theme` block, where a custom property named `--color-navy-600` automatically generates `bg-navy-600`, `text-navy-600`, `border-navy-600`, and so on. Three ramps are defined — `navy-*`, `gold-*`, and a neutral `ink-*` whose greys carry a faint navy cast so the darks read as one family instead of two unrelated ones. There are no raw hex values in any component file except the four pipeline-segment colours, which are inline because they're passed to `style={{ backgroundColor }}` for a dynamically-sized bar.

**Give each colour exactly one job.** Navy means *action*: buttons, links, active nav, focus rings. Gold means *emphasis*: the active-nav marker, key figures, the cover badge. Because the roles are disjoint, nothing has to be decided case by case. The discipline also forced a real decision — "draft" status was originally an amber chip, which collided with gold; it became a neutral grey chip so gold stays unambiguous.

**Contrast is a constraint, not a preference.** Gold `#E4A830` against white is roughly 2.3:1 — far below the 4.5:1 WCAG AA threshold for body text. So gold is *never* a text colour on a light background. It appears as a fill with dark navy text on top (about 8:1, comfortably passing), or as the darkened `--color-gold-700` `#8A6212` when gold-flavoured text is genuinely needed. This is why the interface leans navy: the brand's second colour simply cannot carry text at small sizes.

**A dark sidebar was tried and rejected.** The obvious "premium admin" move is a near-black rail. It failed here for a concrete reason: the logo is a navy wordmark on a transparent background, so on a dark navy rail it became unreadable. The rail went white instead and the drama moved to a single deep-navy panel on the dashboard, where no logo competes with it. The general lesson — let the asset you must display dictate the chrome around it.

**Spend boldness once.** Exactly one element is loud: the suggestion pipeline panel, a dark block with a stacked proportional bar. Everything else is white panels, hairline `ink-200` borders, and almost no shadow. Lists are rendered as hairline-divided rows (`.row-list`) rather than a grid of individually floating cards, which is both calmer and less markup.

**Status is never colour alone.** Suggestion rows carry a colour-coded left rail matching the pipeline, but the status *word* is always present in the adjacent `<select>`. Colour is an accelerator for scanning, never the only channel — that's a WCAG requirement and it also helps anyone scanning quickly.

### Three concrete bugs worth studying

**1. `@apply` of a custom class silently fails in Tailwind v4.** Writing `.btn-primary { @apply btn ...; }` works in v3 but not v4, where `@apply` only accepts real utilities, not classes you defined in `@layer components`. The fix was to share the base with a selector list instead:

```css
.btn-primary, .btn-secondary, .btn-quiet, .btn-danger { @apply inline-flex items-center ...; }
.btn-primary { @apply bg-navy-600 text-white ...; }
```

**2. Horizontal scroll on mobile from `min-width: auto`.** The dashboard's two columns are a CSS grid. Grid and flex children default to `min-width: auto`, meaning they refuse to shrink below their content's intrinsic minimum — so a long event title forced the track wider than a 390px viewport and the whole page scrolled sideways. `truncate` on the inner text does nothing about this, because the *track* is what's oversized. The fix is one class, `min-w-0`, on each grid child. This is probably the single most common responsive-layout bug in flex/grid code; the way to find it is to compare `document.documentElement.scrollWidth` against `clientWidth` rather than eyeballing a screenshot.

**3. Two React correctness warnings, both real.** `oxlint` flagged (a) closing the mobile nav from a `useEffect` on route change, and (b) calling `Date.now()` during render. The first was fixed by closing the drawer in the `onClick` that caused the navigation — an effect synchronising state that an event already knows about is redundant. The second was fixed with `useState(() => Date.now())`, which pins the timestamp once per mount; calling `Date.now()` in the render body makes output depend on *when* React happened to render, which is exactly the impurity that breaks under concurrent rendering.

### Markup choices that the tests depend on

`SuggestionsPage.test.tsx` locates a row with `item.closest("li")`. The original markup used nested `<div>`s, so that test could not pass. Rendering lists as real `<ul>`/`<li>` fixed it and is also what a screen reader needs to announce "list, 8 items." Semantic markup is not decoration — here it is load-bearing for the test suite.

Similarly, "Remove"/"Delete" actions were previously `opacity-0 group-hover:opacity-100`. Hover-only controls are invisible to keyboard and touch users, so they are now always visible and styled quietly instead.

### Honesty in the interface

Three status indicators were removed: a hardcoded green "API Connected" dot in the sidebar, an "API: 8000 Connected" badge in the top bar, and a "SYSTEM ACTIVE / v1.0 Pro" pair. None performed a health check — they were static markup that would have kept claiming success while the API was down. **An indicator that cannot fail is worse than no indicator**, because it actively misleads during exactly the incident it appears to be reporting on. If you want these back, wire them to a real poll of `/health` and let them render a failure state.

The typeface is currently Plus Jakarta Sans, loaded from Google Fonts in `admin/index.html` and set as both `--font-sans` and `--font-display` in the `@theme` block.

## 8–9. Flutter client (`client_app/`)

Same approach as the admin: a fresh agent, contract doc only, no backend source reading. Structure is `lib/{core,models,features/{events,committee,suggestions}}`.

Note what's missing against `CLAUDE.md` section 10: **there is no `features/auth/` and no `features/profile/`**, for the same reason the backend has no auth router — that layer was removed. There is no `core/token_storage.dart`, and `core/router.dart` has no auth-gated redirect, because there's no session to gate on. `flutter_secure_storage` may still sit in `pubspec.yaml` without anything importing it.

Layering mirrors the React app's, adapted to Riverpod:
- `core/api_client.dart` — the Dio instance. `core/api_exception.dart` — the same dual-shape error normalization as the React side (`{"detail": "..."}` vs `{"detail": [...]}`); two clients, same two error shapes, so both needed the same helper. `core/router.dart` — go_router route table. `core/app_shell.dart` — the bottom-nav scaffold the tabs live in.
- Each feature folder follows the same three-layer split: `data/` (a repository that talks to the API), `application/` (Riverpod providers), `presentation/` (screens). Tracing one feature end to end — say `features/events/` — teaches the whole app, because the other two are the same shape.
- Tests override the repository provider with a fake object rather than mocking Dio at the HTTP layer — simpler, and just as effective for testing widget behaviour.

**One real bug caught in review, not by the agent's own testing**: `pubspec.yaml` still said `name: studio_client` / `"Studio 006 client portal."`, left over from the old domain — the agent didn't touch it since it was focused on dependencies. Renaming a Dart package name isn't just a string edit though — five test files imported `package:studio_client/...` to reach code in `lib/`, and those imports break silently (a package name mismatch is a compile error, not a runtime one) if you rename the package without updating them. Fixed by renaming the package *and* grepping for every `package:studio_client` import, updating all five, then re-running the full test suite to confirm nothing broke. Worth remembering: renaming anything that other files reference by name needs a repo-wide search, not a single-file edit — this is exactly the kind of thing "trust but verify" as a review habit catches that reading a summary alone wouldn't.

Also worth noting as a deliberate constraint, not an oversight: `url_launcher` isn't in `CLAUDE.md`'s approved package list, so LinkedIn links in the committee screen copy the URL to the clipboard instead of opening a browser. A stricter reading of the spec over a more "normal" UX — flagged in a comment rather than quietly adding a dependency the spec didn't name.

## 10. CI, Docker, docs

- `backend/Dockerfile` — `pip install` then `alembic upgrade head && uvicorn ...` as the container command, so a fresh deploy always migrates before serving.
- `.github/workflows/ci.yml` — three independent jobs (`backend`, `admin`, `client_app`), each scoped to its own directory. The backend job spins up a real Postgres as a GitHub Actions *service container* (not SQLite) — the test suite genuinely needs Postgres-specific behavior (native enums, `ON DELETE CASCADE`), so faking it with SQLite in CI would test something subtly different from production.
- This file, `docs/api-contract.md`, and `docs/data-model.md` are the three documents meant to answer "what does this do and why" without reading source — the top-level `README.md` links all three plus the setup steps.

## What's absent

Checked against the working tree, not against intent. Roughly in order of how much it matters:

**1. Authentication — the whole layer.** No `/auth/*` endpoints, no `password_hash` or `role` on `users`, no JWT anywhere in either client, no login screen, no route guards. Every "admin" endpoint is open. See section 2.

**2. The AI suggestion engine** — `CLAUDE.md`'s headline feature. No `app/ml/suggestion_engine.py`, no TF-IDF, no KMeans, no sentiment scoring, no `/suggestions/analyse`, no `/suggestions/themes`, no Themes view in the admin. The `suggestions` table *does* have `theme_id`, `theme_label` and `sentiment` columns, always `NULL`, waiting for it.

**3. `ml_eval/`** — the directory exists but holds only `.gitkeep`. No labelled sample, no clustering-agreement script. `CLAUDE.md` says the resulting number "goes on the CV"; that number does not exist yet.

**4. Deployment.** Nothing is hosted. `backend/Dockerfile` and both frontend builds are deploy-ready, and `.github/workflows/ci.yml` exists, but no Render/Vercel/Netlify/Supabase resources have been created. The "Definition of done" in `CLAUDE.md` ("all three deployed and reachable by URL") is not met.

**5. Smaller contract gaps**, each flagged in code comments rather than silently worked around: no photo reorder endpoint, no `PATCH /committee/{id}` (so members can be added and removed but not edited).

### If you're picking this up to study or continue

The build order in `CLAUDE.md` section 13 still holds; steps 1–4 and 6–10 are largely done *except* for auth, which was step 2. The highest-value next move is either re-adding auth (it is what makes the admin panel meaningfully "admin") or building the clustering engine (it is what makes the project distinctive). They're independent — neither blocks the other.

One caution: `docs/api-contract.md` still documents the `/auth/*` endpoints. Treat it as the intended contract, not a description of what's running, and verify against `backend/app/main.py`'s router registrations before building anything against it.
